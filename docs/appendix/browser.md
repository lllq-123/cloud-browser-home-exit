# 附录 · 给浏览器分流，留下能继续用的页面（通用做法）

> 📎 **通用做法，我们家没在用**：这篇是 Chatty 最早整理的通用写法，跟我们家日用的那套不一样，也没在全新环境里从头到尾跑通过，留给想自己折腾的人参考。照我们家的做法搭，请回[首页](../../README.md)。

先完成[隧道出口检查](tunnel.md#5-海外服务器验出口再验网站)。这一篇的命令都在**海外服务器**上执行。

## 1. 确认你操作的是服务器上的浏览器

本教程接着已有的 Chrome / Chromium 环境配置。通过远程桌面看到的窗口，或 agent 连接的浏览器，都必须运行在这台海外服务器上。

如果现在只有 SSH 终端，还没有可操作的浏览器，先完成[云端浏览器搭建](headless-browser.md)：安装完整 Chromium、扩展，启动专用服务，通过 SSH 转发和 DevTools 的 live view 完成本人登录。那里也说明了无头模式、屏幕、语言和 UA 设置。只有模型进程在服务器上，不会自动给服务器增加一个浏览器。

下面演示**有图形桌面时，新建一个独立浏览器资料目录**。已有自动化浏览器启动脚本的读者，把同样的 PAC 参数加到那份脚本即可；需要重新启动的只是选定的浏览器实例。

## 2. 装入 PAC 规则

在教程仓库根目录执行：

```bash
install -d -m700 "$HOME/.config/xhs-browser"
cp examples/appendix/xhs.pac "$HOME/.config/xhs-browser/proxy.pac"
```

目前规则只匹配 `www.xiaohongshu.com`。我们的环境里，`edith.xiaohongshu.com` 等数据接口可以直连，图片也多数不需要国内出口，所以没有把整个 `xiaohongshu.com` 和 `xhscdn.com` 一起绕回手机。

实际网站有变化时，先定位失败请求的域名再决定怎么调整。**如果关键数据接口也要求国内出口，就把那些经过确认的域名加入规则，并接受浏览时更依赖国内设备。**

主站分支只返回 `SOCKS5 127.0.0.1:1080`，不加 `; DIRECT`。在规则已成功加载的前提下，国内出口断了就明确失败，避免重开页面时又从海外直连。

PAC 加载失败本身仍可能让 Chrome 回退直连，所以必须做下一节的浏览器验证。Chrome 的代理选择和 PAC 回退机制见 [Chromium 官方说明](https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/proxy.md)。

## 3. 已有图形桌面时的简短启动方式

按[无头浏览器一章](headless-browser.md)启动过专用服务的读者，直接继续下一节检查路由；不用再启动第二个进程。下面留给已经有图形桌面的读者。

我们曾在 Chromium 147 headless 环境遇到 `file://` PAC 没生效的情况，因此示例把配置转成 `data:` URL。这样不需要再运行一个 PAC 文件服务器。

以下代码在**服务器图形桌面的终端**运行，需要已安装 Chrome / Chromium 和 Python 3：

```bash
(
set -e
XHS_CHROME_BIN=$(command -v chromium || command -v chromium-browser || command -v google-chrome)
XHS_PAC_URL=$(python3 - <<'PY'
import base64
from pathlib import Path
pac = (Path.home() / ".config/xhs-browser/proxy.pac").read_bytes()
print("data:application/x-ns-proxy-autoconfig;base64," + base64.b64encode(pac).decode("ascii"))
PY
)
"$XHS_CHROME_BIN" \
  --user-data-dir="$HOME/.config/xhs-browser/profile" \
  --proxy-pac-url="$XHS_PAC_URL" \
  --no-first-run \
  https://www.xiaohongshu.com/explore
)
```

如果这个资料目录已经有浏览器进程在运行，重新执行命令可能只是把网址交给旧进程，新的代理参数不会生效。修改规则后先正常退出这个专用实例，再重新启动。

需要 Browser Bridge 时，在**这个资料目录对应的浏览器**里安装扩展。原来另一份 Chrome 里的登录和扩展，不会自动搬过来。

`profile` 保存账号登录信息；它应留在自己的服务器上。远程桌面或浏览器调试接口使用已有的认证、SSH 转发等访问方式，不把未保护的控制端口暴露到公网。

## 4. 由本人登录，并确认路由确实生效

在服务器浏览器中打开主站，检查：

1. 地址仍在 `www.xiaohongshu.com`，没有变成海外站。
2. 完成网页要求的登录或验证，能看到自己的登录状态。
3. 在 DevTools 的 Network 中检查主文档请求；目标是主站网页，代理路径应为本机 SOCKS。若面板未显示足够的连接信息，用 Chrome 的 NetLog 检查实际代理选择。
4. 点进一篇帖子，确认标题、作者和正文确实加载出来。

**curl 能走国内出口，不代表 Chrome 已经读入 PAC。**同理，在 PAC 未匹配的 IP 查询网站上看见海外 IP，是这份分流规则的正常表现，不能据此判定主站也没走隧道。

## 5. 留住这张页面，在页面里面走

把这个标签页作为常驻页，后续通过可见控件操作：

- 使用页面里的搜索框和搜索按钮。
- 点击推荐卡片，在当前页面打开详情。
- 用详情的关闭控件回到列表。
- 使用侧栏进入通知等站内页面。
- 需要新数据时使用页面本身的刷新列表功能。

不要把地址栏刷新、反复 `goto(url)`、不断新建标签页，作为每次动作的固定开头。它们会重新触发整页加载。

我们用的是单页应用的现有行为：地址栏可能变化，但页面内部只请求新数据。**“地址变了”和“整页重新加载了”不是同一件事。**在 Network 中观察 Document 请求，才能区分。

点卡片也不保证永远是页内操作。网站改版、点击位置不同、链接要求新窗口，都可能重新开页；一旦发生，就要把这次操作算成再次开门。

我们还遇到过浏览器“后退”直接退出网站的情况。因此关闭详情优先用当前页面明确的关闭按钮；看到目标内容后再继续下一步，不能只凭地址已变化就认定帖子切换成功。

## 6. 常驻页的寿命由好几层决定

| 层次 | 需要照顾的地方 |
| --- | --- |
| 浏览器 | 保持进程；不要把所有标签统一定时关闭或每天无条件重启 |
| 浏览器内存管理 | 在“性能 / 内存节省”设置中将该站加入保持活动的站点；固定标签不等于不会被丢弃 |
| 自动化工具 | 使用会保留页面的绑定 / 会话，并复用同一页；见 [OpenCLI 配方](agent.md) |
| 自己的清理任务 | 根据明确的标签身份保留它，清理其他闲置页 |
| 网站 | 登录可能过期，页面也可能失效，保留重新打开和登录的流程 |

浏览器重启、崩溃或页面失效以后，用国内出口重新打开主站，再确认账号和页面，重新交给 agent。不要承诺“开过一次，以后永远不用手机”。

## 7. 如何证明常驻页确实减少了依赖

先在一张单独的测试页上完成登录态检查，再在 DevTools Network 中记录一轮：搜索、打开帖子、关闭详情、进入通知。看这些动作是否新增了主文档请求，以及数据请求从哪些域名取得。

我们的日用验证曾在测试页中屏蔽 `www.xiaohongshu.com` 的请求，确认部分页内操作仍能获得新数据。这只能证明**那一轮受测动作**的行为；它不等于实际拔掉手机后所有导航都可用，也不能证明未来的网站更新不会改变接口要求。

若要自己验证“手机离线时还能做什么”，先确认这条隧道没有被其他任务共用，再短暂停止**自己的测试客户端**，执行一轮只读浏览，随后恢复客户端。不要在有人正依赖它时直接停共用服务。

## 常见现象

| 现象 | 先检查什么 |
| --- | --- |
| 仍跳海外站 | 手机进程的真实出口、PAC 是否加载、新参数是否被旧浏览器忽略、目标域名是否匹配 |
| `ERR_PROXY_CONNECTION_FAILED` | 服务器 1080 是否监听、国内客户端是否在线、手机有没有结束进程 |
| 首页能开，图片或内容不出 | 失败请求的域名；它是否需要另行分流；手机端 DNS 与请求超时 |
| 放一会儿页就没了 | 浏览器省内存、工具会话超时、自己的闲置清理 / 重启任务 |
| 地址变了，内容还是旧帖子 | 等待内容更新，核对作者、标题或帖子编号；不要只比 URL |
| 搜索读到上次结果 | 核对当前关键词与本次结果更新，再提取内容 |
| 多个 agent 操作时串页 | 对完整浏览任务排队，避免一个读到一半，另一个把页面切走 |
| 大批量滚动加载不出 | 先小批量阅读。我们自己的适配器也有长列表加载问题，见[验证范围](verification.md) |
